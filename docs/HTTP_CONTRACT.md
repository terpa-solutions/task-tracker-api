# Current HTTP contract

This document describes the implemented API. The [original README](../README.md)
is preserved at the user's request and contains the ticket and the initial state
of the exercise; it does not replace this contract. The rules and their rationale
are in [BUSINESS_RULES.txt](../BUSINESS_RULES.txt). Usage commands are in
[API_EXAMPLES.md](API_EXAMPLES.md), with their verification in
[EXAMPLE_VERIFICATION.md](EXAMPLE_VERIFICATION.md).

Validation responses and public messages are written in English.
Send JSON bodies with Content-Type: application/json. The parser limit
is 100 KB (102400 bytes). The local server listens at http://localhost:3000.

## Operations and successful responses

| Method and route | Accepted body | Success |
| --- | --- | --- |
| GET /health | No body required. | 200, {"status":"ok"}. |
| GET /tasks | Optional query filters. | 200, object containing tasks and message. |
| POST /tasks | title; optional priority and due_date. | 201, saved task. |
| PATCH /tasks/:id | One or more of title, completed, priority, due_date. | 200, updated task. |
| DELETE /tasks/:id | No body required. | 204, no body. |
| POST /tasks/bulk-complete | Only ids, an array of 1 to 500 unique IDs. | 200, {"updated":n}, where n is the number of actual transitions. |

A public task contains exactly these fields:

~~~json
{
  "id": 1,
  "title": "Prepare report",
  "completed": false,
  "created_at": "2026-09-09 01:19:57",
  "priority": "medium",
  "due_date": null
}
~~~

id is an integer from 1 through 500000; completed is a boolean; priority is
low, medium, or high; due_date is valid text or null. created_at continues
to be generated by SQLite. The example does not prescribe the actual creation time.

## GET /tasks: filters and a stable structure

Send each parameter only once. Separate list values with commas;
they are alternatives within that filter (OR). Different filters use AND.
The list is always ordered by ascending ID.

| Query | Result |
| --- | --- |
| /tasks | All tasks. |
| /tasks?priority=low,medium | Low or medium priority. |
| /tasks?priority=low,high | Low or high priority. |
| /tasks?priority=medium,high | Medium or high priority. |
| /tasks?completed=false&priority=low,high | Pending tasks with low or high priority. |
| /tasks?completed=true,false&priority=low,medium,high | All tasks; equivalent to /tasks. |

Individual values are also accepted, for example completed=true or
priority=high. Commas may be encoded as %2C. Unknown values, empty values,
spaces, uppercase values, empty comma-separated items, duplicates, repeated
parameters, unknown parameters, and array/object-shaped parameters return 400.
An error invalidates the entire query.

When results exist, the response is {"tasks":[...],"message":null}. tasks contains
tasks with the structure above; consumers read response.tasks. Without results,
including an empty table, the response remains 200:

~~~json
{
  "tasks": [],
  "message": "No matching tasks found."
}
~~~

This object explicitly replaces the previous bare array. The structure does
not vary according to the number of results.

Coverage: [api-safety.test.ts](../tests/api-safety.test.ts), tests
"GET aplica las seis consultas de filtros y sus resultados coinciden con SQLite",
"una consulta válida sin coincidencias devuelve lista vacía y mensaje en inglés con HTTP 200"
and "GET sin filtros conserva el mismo contrato cuando la tabla está vacía".

## POST and PATCH: fields, omission, and dates

The body must be a JSON object. POST accepts only title, priority, and due_date;
PATCH also accepts completed and requires at least one field. Sending id, created_at,
or any other disallowed property returns 400.

| Field | POST /tasks | PATCH /tasks/:id |
| --- | --- | --- |
| title | Required text, non-empty after trimming both ends. | Same validation when provided; omission preserves the title. |
| completed | Not allowed; created as false. | Only boolean true or false; omission preserves the status. |
| priority | Exactly low, medium, or high; omission defaults to medium. | Same allowed values; omission preserves the priority. |
| due_date | Optional, as defined in the next table. | Changes only when provided, as defined in the next table. |

priority does not accept null, empty strings, spaces, uppercase values, or other types.
It is neither trimmed nor automatically converted to lowercase.

The original ticket says **"optional ISO date string"**. The user subsequently
agreed to a strict **YYYY-MM-DD HH:mm:ss** representation, with a space,
whole seconds, and no timezone, using the appearance of created_at as a
reference. This clarification is an explicit later decision, rather than the
original wording or an RFC 3339 contract. It does not change created_at.

The calendar date and time must be valid. An explicit date must fall on
today or a future day, using the API machine's local day.
Any valid time today is accepted, even if that time has already passed.

| due_date input | POST | PATCH |
| --- | --- | --- |
| Omitted property | SQL NULL; JSON null. | Preserve the value, even if its date is in the past. |
| null | SQL NULL; JSON null. | Remove the date immediately. |
| Exact string "" | SQL NULL; JSON null. | Remove the date immediately. |
| ASCII spaces only, such as "   " | SQL NULL; JSON null. | 400; preserve the entire task. |
| Valid date and time, today or later | Save the exact text. | Save the exact text. |
| Past day, impossible calendar date/time | 400. | 400; preserve the entire task. |
| T, timezone, fractions, surrounding spaces, tabs, line breaks, or incorrect type | 400. | 400; preserve the entire task. |

A PATCH containing both valid and invalid inputs is rejected in full. After parsing,
the route ID is checked first, then task existence, then the body;
a missing task retains its 404. Creation validates before inserting.

Coverage: [task-validation.test.ts](../tests/task-validation.test.ts), tests
"el reloj recibido acepta cualquier hora de hoy y distingue el día anterior" and
"el formato exige espacio, segundos enteros y ningún ajuste de zona horaria";
[api-safety.test.ts](../tests/api-safety.test.ts), tests
"PATCH conserva campos omitidos y fechas históricas, y null o cadena vacía eliminan la fecha"
and "PATCH mixto inválido no aplica ninguno de los cambios ni activa escrituras".

## IDs, deletion, and capacity

PATCH and DELETE require decimal digits in the route and a value from 1 through 500000.
Leading zeros are allowed in that route. Fractions, exponents, signs, and values
outside the range are rejected before accessing the task.

| Case | Status | Body |
| --- | --- | --- |
| Invalid percent encoding in a PATCH/DELETE route | 400 | {"error":"Invalid URL encoding. Use a valid percent-encoded task ID."} |
| Invalid route ID | 400 | {"error":"Invalid task id."} |
| Task 8 missing in PATCH/DELETE | 404 | {"error":"Task 8 not found."} |
| Creation exceeds the limit | 400 | {"error":"Cannot create a task because the ID limit (500000) has been reached."} |
| Successful deletion | 204 | No body. |

The missing-task message substitutes the requested ID for 8.
Deletion does not reset the sequence. Creation without available capacity
neither inserts a row nor changes the sequence.

Routes such as /tasks/% and /tasks/%E0%A4%A fail during Express parameter
decoding. They receive the route-specific 400 before the controller calls
the model, and leave SQLite rows and sequence unchanged. This rule is scoped
to the recognized Express decoding error; an internal URIError retains 500.

Coverage: [api-safety.test.ts](../tests/api-safety.test.ts), tests
"PATCH y DELETE rechazan IDs ambiguos antes de tocar la tarea 1" and
"crea hasta 500000 y devuelve 400 sin cambiar filas o secuencia al agotar el rango".
The four method/path combinations in
[error-handler.test.ts](../tests/error-handler.test.ts) assert the exact
malformed-route response, zero model calls, and unchanged SQLite snapshots.

## POST /tasks/bulk-complete

~~~json
{"ids":[1,2,3]}
~~~

The body accepts only ids: between 1 and 500 unique numeric elements, from 1
through 500000. In the original JSON, each ID must be written using digits only.
Values such as 1.0, 1e0, 1.0000000000000001, signs, strings, null, and other types
are rejected, even if JavaScript converts a representation into an allowed integer.
Repeating the ids property also returns 400, even when its last occurrence
contains an invalid value.

If all IDs exist, only completed=false changes to true.
The response is 200 with {"updated":n}; already completed tasks are valid and
are not counted. A request may return {"updated":0}.

If IDs are missing, return 404 without changing any task and list all
missing IDs in numeric order. Example for IDs 8 and 9:

~~~json
{"error":"Tasks not found: 8, 9."}
~~~

The existence check and the update are atomic. A write failure rolls back
the entire batch. No other field or the sequence is changed;
an existing date in the past is not revalidated.

Coverage: [api-safety.test.ts](../tests/api-safety.test.ts), tests
"bulk-complete cuenta transiciones reales, acepta el ID máximo y conserva los demás datos",
"bulk-complete rechaza atómicamente los IDs inexistentes y los informa en orden numérico"
and "bulk-complete revierte escrituras parciales ante un fallo SQLite y oculta los detalles internos".

## Validation errors: structure and order

Validation rejections use 400 and an errors array, even for a single error:

~~~json
{
  "errors": [
    {
      "field": "completed",
      "message": "Field \"completed\" must be a boolean: true or false."
    }
  ]
}
~~~

One message is returned per field, in this order:

| Operation | Order |
| --- | --- |
| POST/PATCH | title, completed, priority, due_date; then unknown fields by name. |
| GET /tasks | completed, priority; then unknown fields by name. |
| Batch | ids; then unknown fields by name. |
| Non-object body, empty PATCH, or parser error | field: "body". |

The following are literal messages or identified templates. Field, index,
and example placeholders are replaced with the indicated value. In the
unknown-property message, FIELD represents the received name.

### POST/PATCH messages

- Non-object body: The request body must be a JSON object.
- Invalid title: Field "title" must be a non-empty string; it is required when creating a task.
- Invalid completed: Field "completed" must be a boolean: true or false.
- Empty PATCH: Provide at least one of "title", "completed", "priority", or "due_date" to update.
- Unknown property: Field "FIELD" is not allowed in this operation.

Invalid priority in POST:

~~~text
Field "priority" must be exactly "low", "medium", or "high", in lowercase with no spaces. Omit "priority" when creating a task to use "medium".
~~~

Invalid priority in PATCH:

~~~text
Field "priority" must be exactly "low", "medium", or "high", in lowercase with no spaces. Omit "priority" when updating to keep its current value.
~~~

Invalid date format or type in POST:

~~~text
Field "due_date" must be a string in YYYY-MM-DD HH:mm:ss format, without a timezone, fractional seconds, surrounding spaces, tabs, or line breaks. Omit "due_date", or send null, an empty string, or ASCII spaces only to create without a due date.
~~~

Invalid date format or type in PATCH:

~~~text
Field "due_date" must be a string in YYYY-MM-DD HH:mm:ss format, without a timezone, fractional seconds, surrounding spaces, tabs, or line breaks. Send null or an empty string to remove the date; omit "due_date" to keep it. Spaces-only strings are not allowed.
~~~

Invalid calendar date/time and past day, respectively:

~~~text
Field "due_date" must contain a valid calendar date and time in YYYY-MM-DD HH:mm:ss format.
Field "due_date" must fall on today or a future day, based on the API machine's local date. Use YYYY-MM-DD HH:mm:ss.
~~~

### Filter messages

Invalid value:

~~~text
Query parameter "completed" contains an invalid value. Use "true", "false", or "true,false", in lowercase, without spaces or empty list items. Example: completed=false.
Query parameter "priority" contains an invalid value. Use one or more of "low", "medium", or "high", separated by commas, in lowercase, without spaces or empty list items. Example: priority=low,high.
~~~

Repeated parameter and duplicate selection:

~~~text
Query parameter "<field>" must appear only once. Use a comma-separated list instead. Example: <example>.
Query parameter "<field>" must not repeat values. Include each selected value once. Example: <example>.
~~~

For completed, the template example is completed=true,false; for priority it is
priority=low,high. Unknown parameter:

~~~text
Query parameter "<field>" is not allowed. Use only "completed" and "priority", each once with comma-separated values. Example: completed=false&priority=low,high.
~~~

### Batch messages

~~~text
Field "ids" is required and must be an array of task IDs. Example: {"ids":[1,2]}.
Field "ids" must contain at least one task ID. Example: {"ids":[1,2]}.
Field "ids" must contain at most 500 task IDs. Split larger requests into separate batches.
Field "ids" must not repeat IDs. Include each task ID once. Example: {"ids":[1,2]}.
Field "ids" must appear exactly once. Example: {"ids":[1,2]}.
~~~

Invalid element type or range:

~~~text
Field "ids" must contain integer numbers from 1 through 500000, without strings or null. Example: {"ids":[1,2]}. Invalid item at index <index> (zero-based).
~~~

Invalid numeric notation:

~~~text
Field "ids" must use decimal digits only, without signs, fractions, or exponents. Invalid item at index <index> (zero-based). Example: {"ids":[1,2]}.
~~~

The index starts at zero. Non-object bodies and unknown properties use the
common messages. If the captured JSON text required to validate the notation
is unavailable, the body error is:

~~~text
Send a JSON body with Content-Type: application/json.
~~~

## JSON parser and internal failures

Parser errors use {"errors":[{"field":"body","message":"..."}]}:

| Status | Cause | Literal message |
| --- | --- | --- |
| 400 | Malformed JSON. | Invalid JSON. Use double quotes and remove trailing commas. |
| 400 | Inconsistent length. | Invalid request body length. Send a complete JSON body with a correct Content-Length. |
| 400 | Interrupted reception. | The request body was interrupted. Send the complete JSON body again. |
| 400 | Corrupted compressed body. | Invalid encoded request body. Send valid JSON with the correct Content-Encoding. |
| 413 | Exceeds 100 KB. | Request body is too large. Maximum size is 100 KB. |
| 415 | Unsupported charset or content encoding. | Unsupported request encoding. Use UTF-8 JSON with a supported content encoding. |

These validations occur before the controller. Delivering an error depends
on the connection remaining open. The parser retains verified compatibility
with UTF-8 with BOM, UTF-16LE, and gzip; recommending UTF-8 does not mean
rejecting all other supported encodings.

An unexpected failure returns 500:

~~~json
{"error":"Internal server error."}
~~~

The cause is logged on the server without copying the entire body or exposing
internal details. If headers have already been sent, the error is delegated
instead of attempting another response. An internal SyntaxError is not
mistaken for an error in received JSON. An internal URIError is not classified
as malformed route input solely because of its class.

Source: [error-handler.ts](../src/middleware/error-handler.ts).
Coverage: [error-handler.test.ts](../tests/error-handler.test.ts),
